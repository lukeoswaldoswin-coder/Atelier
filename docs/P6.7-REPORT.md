## 三、数据库结构是否变化

**是，新增一张表（迁移 006，纯追加）。**

```sql
CREATE TABLE time_entry_segments (
  id         TEXT PRIMARY KEY NOT NULL,
  entry_id   TEXT NOT NULL REFERENCES time_entries (id)
               ON UPDATE CASCADE ON DELETE CASCADE,
  started_at TEXT NOT NULL CHECK (started_at GLOB <UTC>),
  ended_at   TEXT NOT NULL CHECK (ended_at   GLOB <UTC>),
  seconds    INTEGER NOT NULL CHECK (typeof(seconds) = 'integer' AND seconds >= 0),
  created_at TEXT NOT NULL CHECK (created_at GLOB <UTC>),
  updated_at TEXT NOT NULL CHECK (updated_at GLOB <UTC>)
);
CREATE INDEX idx_time_entry_segments_entry ON time_entry_segments (entry_id, started_at);
```

### 为什么必须迁移（这是本阶段唯一的结构调整）

执行前核查确认：**`time_entries` 只保存 `started_at` / `ended_at` / `elapsed_seconds`，
不存在任何活跃片段表**。任务会话的 `segmentStartedMono` 只存在内存里（`time-service.ts`）。

因此对于「开始 → 暂停 → 继续 → 结束」且跨越午夜的一次会话，数据库里只有总时长和会话首尾，
**中间活跃片段落在哪一天是不可还原的**。这正是需求 §5.2 明确禁止伪造的情形。

处理方式：
- 迁移 006 **只新增明细表**，不回填、不修改任何既有工时/任务/委托数据；
- 老记录没有片段，走「老记录规则」（见第五节），不伪造精度；
- 新记录从 P6.7 起才有片段，可精确按日归属。

### 数据安全验证（真实库副本，只读源库）

## 四、每日工时的实际统计方式

1. 取区间内 `status='completed' AND deleted_at IS NULL AND merged_into_id IS NULL` 的记录
   （`merged_into_id` 必须排除，否则被合并掉的原记录会重复计数）；
2. 取出这些记录的活跃片段；
3. 用 `attributeEntryToDays()` 把每条记录还原到**本地自然日**；
4. 在 Main 进程按日聚合，返回 `{date, seconds, taskCount, commissionCount, unassignedSeconds}`。

**不使用**创建日期、计划日期、完成日期或会话开始日期代替实际发生日期。

**区间取数用墙钟交集**（`started_at < to AND (ended_at IS NULL OR ended_at > from)`），
而不是 `started_at` 落点——否则 23:40 开始、次日 00:20 结束的记录在次日查不到。

**硬不变量：各日秒数合计严格等于 `elapsed_seconds`**，不重复、不丢失。
该不变量由 23 条单元测试 + 11 条端到端测试守护。

## 五、跨日期工时的分配方式

### 5.1 有片段（P6.7 之后的新记录）

每个片段按真实墙钟起止独立归属日期。一次会话含多个片段时，各片段分别计算。

`23:40 → 00:20` 且连续：
- 11-18：20 分钟
- 11-19：20 分钟

### 5.2 日界定位：二分查找，不依赖「本地 00:00 转 UTC」

`splitSegmentByLocalDay` 用二分查找定位「本地日发生变化」的第一个瞬间。
原因：某些时区在夏令时切换当天的本地 00:00 **并不存在**（时钟从 23:59 直接跳到 01:00），
直接换算会失败或算错。二分只依赖本地日期函数的单调性，对任何时区都成立。

夏令时两侧均已验证：秋季回拨日（25 小时）不重复计算，春季跳变日（23 小时）不丢失。

### 5.3 老记录（P6.7 之前，没有片段）

按墙钟跨度与实际累计的差值判断：

- **差值 ≤ 120 秒** → 视为整段连续活跃，按墙钟占比跨午夜拆分（可信）；
- **差值 > 120 秒** → 中间存在暂停或空闲，活跃时间在会话内的位置**不可知**。
  此时**不伪造精确分布**，整笔归到会话开始日。

真实库实测：6 条已完成记录中 1 条跨本地午夜（23:38→00:06，差 10 秒，属连续），
0 条属于「跨午夜且不可知」。即当前用户数据尚未受该限制影响。

### 5.4 超量保护（实现中发现并修复）

用户手工修改工时起止时间（`updateCompleted` 会重算 `elapsed_seconds`，但不改写历史片段）
后，片段合计可能**大于** `elapsed_seconds`。若直接采用片段，日历会比工时记录页多算，
造成同一笔工时重复累计。

处理：`elapsed_seconds` 始终是权威值。超量时按比例缩放各片段，保持相对分布，
余数补给最长的一天，保证合计严格等于 `elapsed_seconds`。

## 六、新增 IPC 与查询逻辑

| 通道 | 输入 | 输出 |
|---|---|---|
| `calendar:activity` | `{from, to}`，`from<=to`，跨度 ≤ 62 天 | `{days: [{date, seconds, taskCount, commissionCount, unassignedSeconds}]}` |
| `calendar:day-detail` | `{date}` | `{date, totalSeconds, unassignedSeconds, tasks[], unassignedEntryIds[], commissions[]}` |

- 两个通道均经 `ipcContracts` 登记，**Zod `strictObject` 校验**（多余字段直接拒绝）；
- Renderer 无法直接访问数据库，全部经主进程；
- 月视图**一次请求整个 42 天网格**，不逐格发 IPC；周视图只查该周；点击某天才取明细；
- 日期范围上限 62 天，防止渲染进程请求超范围数据；
- 片段查询按 400 个 id 分批，避开 SQLite 变量上限；
- 片段表不存在时两级降级（`sqlite_master` 探测 + try/catch），日历不会因迁移未跑整页崩溃。

**索引**：沿用既有的 `idx_time_entries_started` / `idx_time_entries_task`，
新增 `idx_time_entry_segments_entry (entry_id, started_at)`——这是新表必需的，
因为按 `entry_id IN (...)` 批量取片段。未为形式而新增其他索引。

## 九、尚存限制

1. **老记录（P6.7 之前）没有活跃片段**。中间有暂停且跨午夜的老记录，每日分布不可还原，
   整笔归到会话开始日。当前真实库中此类记录为 0 条。
2. **合并产生的工时记录**（`time:merge`）没有片段，走老记录规则，按日精度可能退化
   （不丢秒、不重复）。
3. **手工修改工时起止时间**后片段不会同步更新；靠超量缩放保证合计守恒，
   但该笔工时的跨日分布精度会退化。
4. **重启恢复**：恢复前那段累计没有片段，余量归到会话开始日（P6.6 既有语义，不重复计入）。
5. 日历侧栏在 w-80 下四区内容较长，需要滚动；未做专门的视觉压缩。
6. 日期数字由 `<span>` 改为 `<button>`（为了「点击日期」有可访问名称），视觉未变。
7. 任务页「定位」只高亮并滚动到可见区，不改变用户当前的筛选条件。
