# Atelier 画师工坊

画师工坊是面向独立画师的**画师委托与创作管理**桌面软件（Windows）。数据只保存在本机，不上传云端，不做团队协作。

核心功能：

1. 委托与客户管理；
2. 绘画任务管理（阶段分类、状态、预计工时、排序、归档）；
3. 日历与手动排程（任务计划日期与委托截止日期分开）；
4. 实际工时记录；
5. 简单辅助排期建议（可解释、用户确认后写入计划日期）；
6. 数据备份、恢复与导出。

**明确不做**：团队项目管理、复杂工作流引擎、流程模板 / 每委托自定义流程、每日绘画容量、可绘画时间窗口、自动排班算法、任务依赖与自动拆分。

> 当前进度：**P0 + P1.1 + P1.1.5 + P1.2.1–P1.2.5 委托管理 + P2 绘画任务 + P3 日历与手动排程 + P4 实际工时记录 + P5 简单辅助排期已完成并实际运行验证通过**；P2/P3/P4 已验收（`p2-baseline`/`p3-baseline`/`p4-baseline`），**P6 尚未开始**。

## 二、如何启动

### 最简单的方式（推荐）

双击项目根目录的 **`启动Atelier.cmd`**。

它会自动：找 Node.js → 找 pnpm → 首次运行时安装依赖 → 打开 Atelier 窗口。

```powershell
pnpm install      # 首次运行，安装依赖
pnpm dev          # 启动开发版窗口（带热更新）
```

| `pnpm dev` | 启动开发版（热更新） |
| `pnpm build` | 构建生产版本到 `out/` |

| `pnpm typecheck` | 检查 TypeScript 类型（主进程 + 渲染进程各一次） |

## 四、安全架构

1. **进程隔离**：`nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`。渲染进程拿不到 Node.js、文件系统或 `require`。
2. **受控 IPC**：渲染进程只能调用 preload 通过 `contextBridge` 暴露的具名方法（客户、委托、任务的读写），不能自行指定通道名或监听主进程事件。
3. **契约校验**：每个通道在 `src/shared/contracts.ts` 中声明输入/输出 Zod schema，主进程在边界处校验，错误数据不会流到界面。
4. **来源校验**：IPC 调用会检查发起方 frame 的地址，只接受本应用界面（开发时为 Vite 服务器 origin，打包后为本地 `file://`）。
5. **窗口加固**：禁止打开新窗口、禁止导航到外部地址、禁止挂载 `webview`、拒绝一切权限申请（摄像头、通知等）。
6. **错误隔离**：处理器异常只在主进程记录完整信息，回给渲染进程的是稳定错误信息，不泄露内部细节。
7. **CSP**：生产构建自动注入严格 Content-Security-Policy（`script-src 'self'` 等）。

开发模式下不注入 CSP，因为 Vite 需要内联脚本与 WebSocket；这是开发环境的已知取舍。

## 六、数据库（P1.1 / P1.1.5 / P2）

### 存储位置

- **正式运行**：`%APPDATA%\atelier\atelier.db`（Electron 的用户数据目录，**不在项目源码目录**）。
- **自动化测试**：通过环境变量 `ATELIER_USER_DATA_DIR` 指向临时目录，不会碰真实数据。

WAL 模式下同目录还会出现 `atelier.db-wal`、`atelier.db-shm`，这是 SQLite 的正常伴生文件。

### 表结构

**clients（客户）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT 主键 | UUID |
| name | TEXT NOT NULL | 客户名，非空 |
| contact / note | TEXT | 联系方式、备注 |
| created_at / updated_at | TEXT NOT NULL | UTC ISO 8601 |
| archived_at | TEXT | 归档时间，NULL 表示未归档 |

**commissions（委托）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT 主键 | UUID |
| client_id | TEXT NOT NULL → clients(id) | 外键，`ON DELETE RESTRICT` |
| title / description / type | TEXT | 标题、需求说明、委托类型 |
| status | TEXT | `draft` / `active` / `completed` / `cancelled` |
| priority | INTEGER | 1（最高）– 5（最低） |
| deadline_kind | TEXT | `none` / `date` / `datetime` |
| deadline_date | TEXT | 仅 date 型使用，`YYYY-MM-DD` |
| deadline_at | TEXT | 仅 datetime 型使用，UTC ISO |
| deadline_timezone | TEXT | 仅 datetime 型使用，创建时的 IANA 时区 |
| quote_amount_cents | INTEGER | **可空**：NULL 未报价，0 免费，>0 报价 |
| paid_amount_cents | INTEGER NOT NULL | 已收金额（整数分） |
| payment_status | TEXT | 由金额推导：`unquoted` / `not_required` / `unpaid` / `partial` / `paid` |
| completed_at | TEXT | 完成时间：进入「已完成」时写入，离开时清空；与状态保持一致 |
| created_at / updated_at | TEXT NOT NULL | UTC ISO 8601 |
| archived_at | TEXT | 归档时间 |

**tasks（绘画任务，P2）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT 主键 | UUID |
| commission_id | TEXT NOT NULL → commissions(id) | 外键，`ON DELETE RESTRICT` |
| title / description | TEXT | 任务标题、备注 |
| stage | TEXT | `draft` / `lineart` / `color` / `final` / `other`（草稿/线稿/上色/完稿/其他） |
| status | TEXT | `todo` / `doing` / `done` |
| estimated_minutes | INTEGER | 可空；预计工时（分钟），整数、非负、≤ 30 天 |
| planned_date | TEXT | 可空；计划日期（纯 `YYYY-MM-DD`，真实日历校验），NULL = 未安排；与委托截止完全独立 |
| sort_order | INTEGER | 同一委托 + 同一阶段内的手动排序 |
| completed_at | TEXT | 完成时间；CHECK 强制 `done ⇔ 非空` |
| created_at / updated_at | TEXT NOT NULL | UTC ISO 8601 |
| archived_at | TEXT | 归档（软删除），不计入进度 |

**任务与委托的状态联动**（主进程事务内完成）：

- 进行中的委托，在**明确把最后一个任务标记完成**时自动完成（归档任务不算完成）；
- 已完成委托一旦出现未完成任务（新增、恢复归档、重新打开），自动回到进行中；
- 有未完成任务时，手动完成委托会被拒绝（`TASKS_INCOMPLETE`）；
- 草稿、已取消、已归档的委托不参与自动联动。

**time_entries（工时记录，P4）**

| 字段 | 说明 |
| --- | --- |
| id | UUID |
| task_id | 可空 → tasks(id)；NULL = 未分配 |
| source | `manual` / `auto` |
| status | `running` / `paused` / `completed` |
| started_at / ended_at | 墙钟观察值（UTC） |
| elapsed_seconds | **统计权威值**（单调时钟累计；不是 `ended-start`） |
| last_heartbeat_at | 最近检查点（崩溃恢复用） |
| app_key | 自动记录的应用标识；不存窗口标题/路径 |
| clock_skew_seconds | 结束时墙钟差与实际累计的偏差，用于保留系统时间异常信息 |
| merged_into_id / deleted_at | 合并溯源 / 软删除 |

- 部分唯一索引保证同一时刻最多一个手动计时、一个自动片段。
- **手动与自动互斥**：手动计时运行期间自动监测只观察，不创建记录；手动结束后自动恢复独立记录（默认未分配），避免重复计时。
- 自动记录每 30 秒写检查点；崩溃时按检查点结算，不补算停机时间。
- 合并只允许同任务、同来源（自动还要求同软件）；旧记录软删除并保留 `merged_into_id`。

**app_settings**：键值配置（自动监测开关、支持软件、空闲阈值）。

**schema_migrations（迁移记录）**：`id`、`name`、`applied_at`。

数据库层用 CHECK 约束兜底：日期形状与真实日历合法性、截止时间三态互斥、金额为整数且非负、金额与付款状态自洽（等价于禁止超额收款）。

### 截止时间的三种形态

| 形态 | 存储 | 显示 | 用途 |
| --- | --- | --- | --- |
| none | 三个截止字段全为 NULL | “未设置” | 还没约定交稿时间 |
| date | 只存 `YYYY-MM-DD`，**不存时区** | 原样显示，**绝不做时区换算** | “某月某日前交稿” |
| datetime | UTC 瞬间 + 创建时 IANA 时区 | 默认按**创建时区**显示，不随系统时区漂移 | “某日 18:00 交稿” |

- 日期型不把 23:59 写入数据库；排期需要“当天结束”时按基准时区实时计算。
- 日期型的逾期基准是**当前系统本地日期**（`today > deadline_date` 即逾期）；以后如引入“工作时区”设置再改为按工作时区判断。
- 时刻型的时区换算只允许在 `src/shared/time.ts` 里实现，并处理夏令时：不存在的时间（春季跳变）拒绝，重复的时间（秋季回拨）取较早的一次。

### 金额与付款状态

| quote_amount_cents | 含义 | 允许收款 | 派生状态 |
| --- | --- | --- | --- |
| NULL | 未报价 | 否 | `unquoted` |
| 0 | 免费委托 | 否 | `not_required` |
| > 0 | 正常报价 | 0 ≤ 已收 ≤ 报价 | `unpaid` / `partial` / `paid` |

规则：

- 付款状态**只由金额推导**，输入契约里没有 `paymentStatus`，渲染进程提交该字段会被 `.strict()` 拒绝；
- 超额收款拒绝（错误码 `OVERPAY`）；报价降到已收金额以下拒绝（`QUOTE_BELOW_PAID`）；未报价/免费委托登记收款拒绝（`PAYMENT_REQUIRES_QUOTE`）；
- 输出附带两个派生字段（不入库）：`outstandingCents`（未收金额）与 `isSettled`（是否已结清）；
- 列表可用 `paymentStatus` 过滤；`completed` 允许尚有尾款，**未结清**即 `paymentStatus ∈ {unpaid, partial}`。

### 迁移机制

迁移写在 `src/main/db/migrations.ts`，按 id 递增排列。每次启动 `applyMigrations()` 会：

1. 确保 `schema_migrations` 表存在；
2. 只执行尚未记录的迁移，且全部放在**同一个事务**里，任一失败整体回滚；
3. 重复启动幂等，不会重复建表；
4. 迁移清单本身会被校验（id 唯一、递增、必须有 SQL 或执行函数）。

现有迁移：

- `001-initial`：clients / commissions 基础表；
- `002-deadline-and-payment`：重建 commissions（截止时间三态、金额可空、付款状态五态），并回填旧数据：
  - 旧的 `quote_amount_cents = 0` 一律视为**未报价**（旧默认 0 只代表“没填”，不代表免费）；
  - 旧的截止时间一律迁移为 `datetime`，时区取迁移执行时的系统时区（旧表未存时区，只能近似）；
  - 旧状态按金额重新推导，忽略原值。
- `003-tasks`：新增 tasks 表与 3 个索引；commissions 增加 `completed_at`，并用 `updated_at` 为历史已完成委托**近似**回填完成时间（P2）。
- `004-task-planned-date`：tasks 增加 `planned_date`（可空、真实日历校验）与 2 个索引；只追加列，不重建表（P3）。
- `005-time-entries`：新增 `time_entries` 与 `app_settings`、部分唯一索引与 CHECK 约束；只新增表，不改既有数据（P4）。

**迁移前自动备份**：文件数据库存在待执行迁移时，先执行 `VACUUM INTO 'atelier.db.bak-<UTC时间戳>'` 生成一致快照，再执行迁移；全新空库与 `:memory:` 跳过。备份不会自动删除，迁移失败时可据此恢复（迁移本身仍是前向不可逆）。

表重建走标准流程（建新表 → 复制 → 删旧表 → 改名 → 重建索引 → 主动执行 `PRAGMA foreign_key_check`），全程在迁移事务内；外键违规会让整个迁移回滚。`PRAGMA foreign_key_check` 只返回结果、不会自动抛错，因此 `src/main/db/integrity.ts` 会主动检查并抛错。

内置行为：主进程在启动时用 try/catch 包住数据库初始化，打不开或迁移失败会弹出错误提示并退出，不会带着坏连接继续运行。

### 数据访问链路

```
渲染进程 → window.atelier（preload 白名单）→ IPC → Zod 校验 → 仓储 → SQLite
```

- 渲染进程**没有任何 SQLite 句柄**，也没有 `require`；
- 共 39 个受控通道：
  - `clients:create|list|get|update|archive|unarchive`；
  - `commissions:create|list|get|update|archive|unarchive`；
  - `tasks:create|list|update|reorder|archive|unarchive|list-all`；
  - `calendar:tasks`；
  - `schedule:apply`；
  - `time:status|start|pause|resume|stop|list|summary|update|assign|delete|merge|task-totals`；
  - `monitor:status|set-enabled|set-apps|set-idle|set-idle-enabled`；
  - `app:get-info`。
- 每个通道都有输入与输出的 Zod 契约，脏数据不会越过进程边界；
- 业务错误（“客户不存在”“超额收款”等）回传可读信息，其他异常只记在主进程日志；
- 归档 = 写 `archived_at` 软删除，不物理删除；有委托的客户被外键 `RESTRICT` 阻止删除。

### 时间与金额约定

- 时间统一存 **UTC ISO 8601**（形如 `2026-11-14T05:07:27.533Z`）；
- 时刻型截止按创建时区显示；日期型截止是纯日历日期，永不换算；
- 金额一律 **整数分**，数据库用 `typeof(...) = 'integer'` 约束，Zod 同时拒绝小数与负数。

## 七、Electron 运行时问题与处理（重要）

**现象**：在这台电脑的 `D:\Atelier\project` 目录下直接运行 Electron 二进制时，进程会在启动瞬间崩溃（退出码 `0x80000003`）。同一份文件复制到工作区之外的普通目录则完全正常，与项目代码无关。

排查结论：不是 Electron 版本、不是代码、不是显卡驱动，也不是数字签名——官方安装包 SHA256 校验一致，Electron 44、45 都会崩；通过目录联接、修改权限、清空环境变量都无法解决，判断与该目录在此环境中被特殊挂载/重定向有关。

**处理方式**（已自动化，无需手动操作）：
`scripts/electron-runtime.mjs` 在每次 `pnpm dev` / `pnpm start` / `pnpm smoke` 前做自检：
1. 先尝试直接用 `node_modules` 里的 Electron；
2. 启动失败时，把 Electron 复制到工作区之外的 `D:\Atelier\atelier-electron-runtime`，通过官方支持的 `ELECTRON_EXEC_PATH` / `ELECTRON_OVERRIDE_DIST_PATH` 指向它。

换到正常的电脑上，第 1 步就会成功，不会产生任何额外副本，也不会改变项目行为。该外部目录约 360 MB，删除后下次启动会自动重建。

## 九、已知限制

1. 任务使用固定五阶段（草稿/线稿/上色/完稿/其他），暂不支持每委托自定义流程。
2. 任务没有单独的截止时间、依赖关系、子任务与拖拽排序；排序通过上移/下移完成。
3. 日历为自绘月/周网格，只有日期粒度；不支持拖拽改期、小时视图与多日任务。
4. 一个任务只有一个计划日期；已完成任务保留计划日期并继续显示在日历中，暂不支持「隐藏已完成」。
5. **实际工时以 `elapsed_seconds` 为准**（单调时钟累计）；任务预计工时与进度仍在渲染进程聚合。
6. 搜索与筛选在渲染进程完成；数据量超过约 2000 条时应改为 SQL 查询（当前单人使用足够）。
7. 真实数据目录已有用户数据（截至 P4：1 个客户、1 个委托、1 个任务）；所有自动化验证使用临时数据目录，不会写入正式库。P4 只新增 `time_entries` / `app_settings` 两张表。
8. 自动监测仅支持 Windows，依赖 koffi 的预编译二进制；默认关闭，需要用户在设置中主动开启。
9. 数位笔输入可能不被系统空闲统计识别，导致自动记录提前暂停；可在设置中关闭「空闲检测」，但这会让思考时间也被计入。
10. 自动记录只作为工时参考，不保证等同真实绘画时间；自动产生的是未分配工时，需要手动归属。
11. 手动计时运行期间不产生自动记录；手动结束/暂停后自动记录才恢复，避免重复计时。
12. 合并只允许同一任务、同一来源（自动还要求同一软件）；删除为软删除，记录仍保留在数据库中。
13. 需求说明与优先级目前只读（编辑计划见第十二节附录）。
14. 暂不支持批量操作、导出与自定义快捷键。
15. 日期型截止的逾期基准是“当前系统本地日期”，跨时区旅行时边界可能有一天的差异；后续如引入工作时区设置再固定基准。
16. 时刻型截止在创建时会记录作者时区；旧数据（002 之前）没有时区，只能按迁移时系统时区近似。
17. 第一版不支持多次收款流水、退款与超额收款。
18. 依赖缓存目录 `.pnpm-store/`、`.electron-cache/` 位于项目内（已加入 `.gitignore`），可安全删除。
19. GitHub 直连不通，依赖与 Electron 二进制使用国内镜像。
20. 系统未安装全局 Node.js 时，启动器会回退使用 DSH 自带的运行时；长期建议自行安装 Node.js LTS。
21. 尚未引入路由库：页面切换用 Zustand 状态实现。
22. 打包目前验证到 `electron-builder --dir`（含原生模块加载）；正式安装包在 P6 完成。pnpm 可能提示 koffi 安装脚本被忽略，但其平台预编译包已安装且可用。
23. 排期建议使用固定提前量（1–7 天）与自然日计算，不是每日容量安排；多个任务可能建议同一天，需用户自行调整。
24. 无截止任务会排在近期截止之后、远期截止之前；建议日期始终不早于本地今天。
25. 采纳时校验任务状态、预计工时、委托状态、优先级与截止指纹；任一项变化都会整批拒绝并要求刷新。手动修改计划日期只触发“已安排”冲突，不会误报为建议过期。
26. 建议不保存历史、不做工作日/节假日计算，也不使用 P4 实际工时反推。

- 已取消 / 已归档委托不参与日历；未安排列表只包含未完成、未归档且委托为草稿或进行中的任务。
- 右侧「未安排任务」可直接安排日期；点击日历任务可改期、清除计划、跳转委托详情。
- 日期校验拒绝 `2026-02-30` 这类不存在的日期；计划日期写入支持「不传保持 / null 清除 / 日期更新」的部分更新语义。

**实际工时记录（P4）**

- 任务级手动计时：开始 / 暂停 / 继续 / 结束；顶栏显示当前任务与累计时间。
- 任务行显示「预计 / 实际」，委托详情汇总实际工时；概览页展示今日、本周、未分配与当前计时。
- Windows 自动监测：前台进程 + 空闲检测（默认 3 分钟），支持 Photoshop / Clip Studio Paint / PaintTool SAI / Krita / Blender；每 1 秒探测、30 秒检查点，只在状态变化时切分记录。
- 自动记录默认「未分配」，不猜测任务；手动计时期间不产生自动记录，避免重复计时。
- 工时页：按日期范围查看、全部/未分配筛选、累计合计；可归属、修正起止时间、合并（保留溯源）、软删除。
- 异常恢复：崩溃后手动计时恢复为暂停、自动片段按检查点结算；24 小时超时自动暂停并提示。
- 隐私：只读取前台进程名与空闲时间，不读取标题/路径/键盘内容，不截屏，数据只在本地。
- 迁移 005 新增 `time_entries` 与 `app_settings`；打包后原生模块加载已用 electron-builder 验证。

**简单辅助排期（P5）**

- 日历右侧新增「排期建议」页签，与「未安排」并列，默认仍为「未安排」。
- 建议只覆盖未完成、未归档、未安排，且委托处于草稿/进行中的任务。
- 排序：逾期 → 近期截止 → 本周 → 稍后 → 无截止 → 远期；同级按截止、委托优先级、建议日期、预计工时、阶段与排序稳定排列。
- 建议开始日期 = `max(今天, 截止日期 - 提前量)`；提前量按预计工时 1/2/3/5/7 天（未估 2 天），无截止或逾期建议今天。
- 日期加减使用纯整数日历算法，不经过 UTC 时间戳；`todayISO` 由日历页用 `todayInZone` 生成并显式传入，算法不读系统时钟。
- 每条建议携带输入快照（任务状态、预计工时、委托状态、优先级、截止指纹）；采纳时在**同一事务**内重新校验，任一变化整批回滚，提示刷新。
- 用户勾选、可逐条改日期，点击「采纳选中」后才写入 `planned_date`；已有计划日期只报冲突，绝不覆盖；不修改委托截止。
- 无数据库迁移、无新表/字段/版本系统；不引入容量、时间窗、工作日或依赖调度。

### 2. 「已完成 → 重新打开」的状态语义（已确定）

- **目标状态：active（进行中）**，不是 draft（草稿）。重新打开表示继续在办，而不是回到未开始。
- 不改变：付款状态、已收金额、归档标记、客户关联、报价、截止时间。
- `completed_at` 已在 P2 的迁移 003 中加入，并在进入 / 离开「已完成」时维护；仍没有 `reopened_at`，返工次数统计待后续评估。
- 对 P3 日历：重新打开后该委托视为在办，其任务重新进入日历可用范围（具体可见性以任务状态为准）。
- 对 P5 排期的具体影响：
  - 重新打开的委托属于「未完成」输入，必须重新参与排期计算；
  - 若截止时间已过，会标记为逾期风险，但**不会自动修改客户承诺的交稿日期**；
  - 已完成状态本身不进入排期，重新打开会把它重新计入工作量。
- 后续评估：若要统计「返工次数 / 完成时长」，还需要 `reopened_at` 等字段（届时新增迁移）；`completed_at` 已存在。
